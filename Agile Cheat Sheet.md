# AGILE CHEAT SHEET
by Anthony Palaj

# PROJECT PLANNING

* Set vision.  
* Business case & funding.  
  * Set project delivery date.  
* Establish team.  
* Establish project goals.  
* Create initial product backlog ideas.  
* Set milestones.  
* Initial release plan.

# KEY ROLES

* ### Product Owner

  * The person responsible for defining the features needed in the product for the end user (Customer).  
    * Attributes  
      * Veto rights on creative direction.

* ### Scrum Master

  * Oversees and runs the scrum process. Keeping all scrum related notes, documents and processes up to date.  
    * Attributes: Best suited to someone who will do less production.  
    * Should not be the Product owner.  
    * Has veto rights on Scrum process.

* ### Team

  * Anyone that helps build the product.  
    * Attributes: The Product Owner and Scrum Master can still be Team Members.

# ARTIFACTS

* ### Product Backlog

  * Is a list of prioritized user stories (features) which could go into the product. This list changes and evolves at the end of every sprint (Think of it as a shopping list/Wish list).

* ### Sprint Backlog

  * Is made up of the highest priority user stories. The size of each user story is estimated and committed to for the next sprint.

* ### Burn down chart

  * Shows the progress of a sprint (Completed tasks in a sprint backlog) and the velocity of the project.

# STORY TYPES

Stories are player-focused, rather than just actions for developers to do.

### THEME

* Usually created by the product owner a theme can be seen as a component or feature area of a product.

### EPIC

* Usually created by the product owner, an Epic is a bird’s eye view of requirements. 

### USER STORY

* Usually created by the product owner a user story is something actionable and small enough to fit in a sprint. Stories should deliver a vertical slice of functionality to the user that is valuable and complete by the end of an sprint.

### TASK

* Tasks dissect user stories so that the team know how the story will be completed. Tasks are defined by the people doing the work.

## STORY STRUCTURE

* “As a \[role\] I can \[function\] so that \[rationale\]”.


Note: See [https\://trello.com/b/4uK3oT3p/agile-scrum-rpg](https://trello.com/b/4uK3oT3p/agile-scrum-rpg) for Trello story formatting.

## ACCEPTANCE CRITERIA

User stories, like all Product Backlog Items, should contain or clearly imply an acceptance criteria. These are written on the back of the card ( If using a digital tool you can use the “Description” field.

Acceptance Criteria are a set of statements which clearly expresses in simple language without ambiguity the boundaries and parameters of a User Story/feature which determines when a story is completed and working as expected.

Each Acceptance Criteria has a clear pass/fail result, that specify satisfies both functional and non-functional requirements at the current stage of project integration (There is no partial acceptance, the conditions of satisfaction is either met or it is not).

# SPRINT CYCLE PLANNING

## PREPARATION

* Business case & funding.  
* Vision.  
* Initial product backlog.  
* Initial release plan.  
* Assemble team.

## KICK OFF MEETING

* Identify sprint goal.  
* Set sprint length.  
* Select stories.  
* Review and refine user stories  
  * Breakdown and assign stories/ tasks.  
  * Define acceptance criteria (Stories & tasks).  
  * Assign difficulty and predict time to complete task 0, .5, 1, 2, 3, 5, 8, 13).  
* Review sprint goal and projected sprint outcome.  
* Make sure everyone knows what they are doing.  
* Set daily standup time.  
* Get to work.

## DAILY STANDUP

* Start daily stand up on time every Sprint day.  
* Review project progress and news at the top level.  
* Walk the wall evaluating daily work (From the top right back to the left of the board) addressing the story of each card and the progress made on the card by the individuals assigned to the card.  
  * What did you achieve yesterday? (Card context).  
  * What do you plan to do today? (Card context).  
  * Are there any issues standing in your way? (Card context).  
* Once the wall walk is complete address each team member with the following questions;  
  * Anyone without work or looking for work?  
  * Anyone have anything else?  
  * Done\!

## SPRINT REVIEW

* At the end of the sprint the team demonstrates the completed work to the product owner for review. The product owner can then decide if the result is a shippable product or requires further iteration.

**IMPORTANT NOTES**

* The Wall should accurately represent the state of your current build. Only things in the build you can play / show should be ‘Done’.  
* The Burndown Chart will show how many stories were completed and the projects current status.

## PRODUCT INCREMENT 

* If approved clean up, pack (Deploy eg: Update) and document build.

## SPRINT RETROSPECTIVE

* Talk about your velocity – Was the amount of work taken on both accurate, and ambitious?  
* Talk about what you learned from the sprint.  
* Talk about things you think you’ll need to do next sprint, and keep a note on that for your next Kick-Off Meeting.

**Retrospective meeting agenda**

* Goal & Outcome  
* Positives/Negatives  
  * Went well  
  * Went Poorly  
* Actionable Items  
  * Eg: Update product backlog.
